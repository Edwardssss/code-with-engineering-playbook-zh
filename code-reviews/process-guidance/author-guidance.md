# 作者指南

## 好好写你的拉取请求（PR）描述

* 给 PR 起一个描述性的标题，让别人用一句短话就能明白这个 PR 是干什么的。
* 每个 PR 都应有合适的描述，向评审者说明改了什么、以及为什么改。

## 添加合适的评审者

* 按项目规范给 PR 添加一名或多名评审者。理想情况下，至少要有一个人熟悉该项目、或熟悉所用的语言。
* 拉上一个对项目或语言不太熟悉的人，有助于验证改动是否易懂、易读，也能提升团队整体的专业水平。
* 在带客户团队的 ISE code-with 项目中，双方组织都要有人参与评审，以便进行知识转移 —— 见[自定义评审者策略](../tools.md)。

## 乐于接受反馈

围绕设计 / 代码逻辑展开讨论，并按下列方式处理所有评论：

* 如果要求的改动已经完成，则解决（resolve）该评论。
* 如果不打算做要求的改动，就把评论标记为“不予修复”（won't fix），并给出清晰的理由。
  * 如果要求的改动在本任务范围内，“我以后再做”不是可接受的理由！
  * 如果要求的改动超出范围，就为它新建一个工作项（任务或缺陷）。
* 如果看不懂某条评论，就在评审里直接提问，而不是私聊。
* 如果讨论串越滚越长却没有结论，就和评审者约个会（打个电话，或者走过去敲门）。

## 使用检查清单

创建 PR 时，最好在描述里附上一份该 PR 的目标清单。这有助于评审者把注意力放在代码改动的关键区域上。

## 把任务链接到你的 PR

把对应的工作项 / 任务链接到 PR 上。工作项和 PR 之间不必重复信息，但如果任一方缺少细节，两者合起来就能给评审者提供更多背景。

## 代码在评审前应当有注释

如果你无法避免大型 PR，那就把改动的说明写进去，让评审者更容易理解代码；用清晰的注释让评审者能看出每个代码块的目标。

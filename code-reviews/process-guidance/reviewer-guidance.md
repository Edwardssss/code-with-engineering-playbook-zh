# 评审者指南

由于部分评审工作可以交给 linter 之类的工具自动完成，人类评审者可以专注于架构与功能上的正确性。人类评审者应关注：

* 代码所承载的业务逻辑是否正确。
* 新增或修改的测试是否正确。
* 代码所反映的整体设计决策是否“可读”、可维护。
* 团队为每种编程语言维护的常见错误检查清单。

代码评审应当使用下面的指引和检查清单，以确保评审积极、有效。

## 通用指引

### 理解你正在评审的代码

* 逐行读完整份改动。
* 如果这只是利益相关方的评审，那么除非跑起来有助于你理解代码，否则不必真的运行该 PR。
* AzDO 会替你排好文件顺序，但你应该按某种符合逻辑的顺序来读，以便理解。
* 如果因为缺乏上下文而无法完全理解某个文件里的改动，就点击查看整个文件，读一读周边代码，或者把改动检出到 IDE 里看。
* 请作者澄清。

### 慢慢来，把注意力锁在范围内

评审代码既不该草率，也不该一次坐得太久。如果你有一堆 PR 要评审，或者代码复杂度很高，建议在两次评审之间休息一下，把精力优先留给最擅长的部分。

始终记住，代码评审的目标之一是**确认对应任务的目标已经达成**。如果你对相邻的、不在本 PR 范围内的代码有疑虑，把它们另开任务处理（例如缺陷、技术债）。不要因为范围之外的问题而卡住当前 PR。

## 营造积极的代码评审氛围

代码评审对产品质量至关重要，它不该变成长篇辩论的赛场，更不该沦为自尊心的较量。重要的是“抓到了一个缺陷”，而不是“谁写出来的”“谁发现的”“谁修好的”。唯一重要的是尽可能交出最好的产品。

## 体谅他人

* 保持积极 —— 多鼓励，对好的做法表示赞赏。
* 把“吹毛求疵”的意见冠以“Nit:”前缀。
* 避免“你”这类指人的说法，改用“我们”或“这一行” —— 代码评审不是针对个人的，措辞很重要。
* 与其下结论，不如先提问。作者那样做可能有正当理由。
* 如果给出直接意见，请解释为什么代码需要改，最好附上示例。
* 谈到改动时，可以用 suggestion 功能（[GitHub](https://docs.github.com/en/github/collaborating-with-issues-and-pull-requests/commenting-on-a-pull-request#adding-line-comments-to-a-pull-request) 和 Azure DevOps 都支持）向 PR 提建议，或者直接向作者的分支提一个 PR。
* 如果来回评论几轮仍无法解决分歧，就快速聊一聊（当面或打电话），或者拉个群讨论，这往往能为后续的 PR 带来一系列改进。别忘了把达成的一致意见及其原因更新到 PR 里。

## 第一遍：设计审视

### PR 概览

* PR 的描述说得通吗？
* 所有改动都合乎逻辑地属于这个 PR 吗，有没有无关改动？
* 必要的话，改动是否同步反映到了 README 或其他文档中？尤其是当改动影响用户如何构建代码时。

### 面向用户的改动

* 如果代码涉及面向用户的改动，有没有 GIF / 图片说明功能？如果没有，这可能是验证 PR 的关键 —— 确保改动确实做到了预期的事。
* 确认 UI 改动看起来正常，没有意料之外的行为。

### 设计

* PR 中各个代码部件的交互是合理的吗？
* 代码是否认识并遵循了既有的架构与编码模式？

## 第二遍：代码质量审视

### 复杂度

* 函数是否过于复杂？
* 是否遵循单一职责原则？函数或类应当只做“一件事”。
* 某个函数是否应该拆成多个函数？
* 如果某个方法的参数超过 3 个，它可能就过于复杂。
* 是否添加了并不需要的功能？
* 代码是否容易被读者看懂？

### 命名 / 可读性

* 开发者为函数、变量等取的名字好吗？

### 错误处理

* 需要的地方，错误是否被优雅且显式地处理了？

### 功能正确性

* 这个 PR 里有没有可能引发竞态条件的并发代码？请仔细读这部分逻辑。
* 代码还能优化吗？例如：是否存在不必要的数据库调用？
* 该功能放在更大的图景里是否合适？会不会对整个系统产生负面影响？
* 有没有安全缺陷？
* 变量名是否泄露了客户特定的信息？
* PII 和 EUII 是否被正确处理？我们有没有把 PII 写进日志？

### 风格

* 有没有多余的注释？如果代码本身不够清晰，那就应该把代码写简单。注释应当用来解释某些代码为什么存在。
* 代码是否遵守我们约定的风格指南 / 规范？我们使用 black、prettier 这类自动化格式化工具。

### 测试

* 测试必须与代码在同一个 PR 里提交（“我接下来再加测试”是不可接受的）。
* 确认测试合理，所做的假设成立。
* 确认边界情况也被覆盖了。
* 测试是理解改动的好入口。先看测试，往往能帮你更快理解改动。

# 常见问题

这里汇总了使用代码评审时常见的问题，以及可能的应对办法。

## 代码评审和拉取请求有什么区别？

拉取请求（PR）是通知“某项任务已完成、可以合入主工作分支（唯一事实来源）”的方式。而代码评审是让某人先把 PR 里的代码过一遍、在合入前做验证；但总体上说，代码评审也可以在 PR 之外进行。

| 代码评审                                          | 拉取请求                                          |
| --------------------------------------------- | --------------------------------------------- |
| 聚焦于源代码                                        | 目的是支撑和促成代码评审。除了源代码，它还可以覆盖更大的范围（例如文档、集成测试、编译等） |
| 目的是在提交 PR **之前**拿到**早期反馈**                    | 不用于**早期反馈**。它是在作者准备合入时才创建的                    |
| 通常是同步评审，反馈周期更快（草稿 PR 是例外）。例如：排定的会议、站在旁边看、结对编程 | 通常是工具辅助的异步评审，必要时也可以升级为同步会议                    |

## 为什么我们需要代码评审？

我们的同行代码评审围绕最佳实践来组织，目的是发现特定类型的错误。就像你仍然会对集体编程产出的代码跑一遍 linter 一样，你仍然应该找人做最后一道把关，确认代码符合预期标准、避开常见陷阱。

## PR 太大了，怎么解决？

把工作项切成小而清晰的块，这样评审者才能独立理解这些代码。团队应当被要求尽早提交：不是等整个产品待办项 / 用户故事全部完成，而是某个单项完成时提交。如果这批工作会导致功能不完整，那就确保它能被关闭，直到完整功能交付为止。

更多信息见[拉取请求 - 规模建议](./pull-requests.md)。

## 如何加快代码评审？

评审太慢可能导致功能交付延迟，并让团队成员产生挫败感。

### 可以采取的措施

* 在工作约定中加入 PR 周转时间（turnaround time）的规则。
* 在站会之后安排一个时段，专门过一遍待评审的 PR，并给没人处理的 PR 指派评审者。
* 指定一名 PR 评审管理员，负责推动流程流转：在 PR 变陈旧时进行指派或提醒。
* 用工具更好地标示陈旧评审 —— 见[自定义 AzDO 任务板](./tools.md)。

## 评审复杂的 PR 时可以用哪些工具？

关于如何脱离 Visual Studio、或在 Visual Studio Code 中完成评审，参见[工具](./tools.md)。

## 如何强制执行代码评审策略？

配置[分支策略](./tools.md)，就可以方便地强制实施代码评审规则。

## 我们结对或集体编程，代码评审该怎么做？

代码评审有两种做法：

1. **结对** —— 应由结对之外的某个人来做代码评审。代码评审的另一大好处，就是把被测代码区域的领域知识传播给团队里平时不碰这块代码的成员。
2. **集体** —— 应由集体中在键盘前时间较少（或完全没上过手）的成员来做代码评审。

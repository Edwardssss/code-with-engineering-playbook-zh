# 评审中的包容性

以下几点说明了为什么代码评审中的包容性很重要：

* 代码评审是软件专业人员工作的重要组成部分。
* 在 ISE，我们要与来自全球的跨文化团队合作。
* 我们的沟通方式会影响团队士气。
* 包容的代码评审会让新开发者感到受欢迎、更快融入团队。
* 粗鲁或针对个人的攻击会让评审变成排挤 —— 人们在评审 PR 时可能会无意中说出粗鲁的话。

## 非包容行为的类型与例子

* **评审分配不公平。**
  * 例如：把绝大多数评审都派给少数几个人，同时把团队里某些成员完全晾在一边。
* **负向的人际互动。**
  * 例如：在代码风格这类主观话题上长时间争辩。
* **有偏的决策。**
  * 例如：评论针对开发者而不是代码。想当然地认为某位开发者写的代码总是好的、于是不好好评审，反过来也一样。

## 包容性代码评审的例子

* 团队里的任何人都应当有机会被分配 PR 去评审。
* 评审者应当分清哪些是个人意见、个人偏好、最佳实践，哪些是事实。围绕个人偏好和意见的争论大多是可以避免的。
* 在评审评论中使用包容性的措辞和语气。例如，用建议式的语气而不是命令式的语气，更容易把观点传达出去。
* 当评审者帮助改进了代码、或者你学到了新东西时，PR 作者向评审者表示感谢是个好习惯。
* 向新开发者或新客户提出代码改动建议时，可以使用“三明治法”：把建议夹在两句赞美之间。例如：“到目前为止做得很好，不过这里我建议做几处改动。另外，我很喜欢这里对 XYZ 的用法，干得漂亮！”

## 给作者的指导

* 力求写出易读、易评审、易维护的代码。
* 重要的是确保看到这段代码的人 —— 无论是评审者还是未来的工程师 —— 都能理解你的动机，以及代码是如何达成目标的。
* 主动寻求有针对性的帮助或反馈。
* 清晰地回答评审者提出的问题。
* 避免巨型提交，改为提交增量改动。规模大、又包含多个文件改动的提交，会导致对代码的不公平评审，评审者的偏颇行为可能在这种情况下被触发。例如：来自资深开发者的一次巨型提交可能未经仔细评审就被批准，而来自初级开发者的一次巨型提交可能永远得不到评审和批准。

## 给评审者的指导

* 假定作者出于善意。
* 写出清晰、详尽的评论。
* 分清主观性、编码取向与最佳实践。关于编码风格和主观编码选择的讨论，最好放到其他场合，而不是 PR 里。PR 不应成为讨论主观编码选择、为此长时间争辩的地方。
* 如果你没有真正理解代码，就不要下“这段代码无法理解”这类评论。更好的做法是与作者沟通一次，先建立基本理解。
* 建议而非命令。评审者应当**建议**改动，而不是**规定**改动，由作者自己决定是否真的接受所提改动。

## 文化与代码评审

在 ISE，我们可能会遇到代码评审不理想的情况，也经常观察到非包容的评审行为。重要的是意识到：特定地域的文化和沟通风格也会影响人们在拉取请求上的互动方式。 在这种情况下，先假定作者和评审者都出于善意，是开始分析代码评审质量的好起点。

## 应对冒名顶替现象

冒名顶替现象是一种心理模式：个体会怀疑自己的技能、天赋或成就，并持续内化地害怕被当作“骗子”揭穿 —— [维基百科](https://en.wikipedia.org/wiki/Impostor_phenomenon)。

正在经历冒名顶替现象的人，可能会觉得提交代码以供评审格外有压力。重要的是认识到每个人都有有意义的贡献，不要让自认为的弱项阻碍贡献。

给作者的一些克服建议：

* 回顾上面提到的指导，确认你的代码改动遵循它们。
* 向同事求助 —— 与一位你能学到东西的资深同事结对编程。

给评审者的一些克服建议：

* 任何人都可能有有价值的见解。
* 一双新眼睛总是受欢迎的。
* 研究这次评审，直到你完全理解它；检查边界情况，寻找改进的空间。
* 如果有不明白的地方，问一个具体而简单的问题即可。
* 如果你学到了东西，随时可以称赞作者。
* 如果可能，与人结对评审代码，这样你们能建立个人联结，对代码进行更深入的讨论。
